# Metrics schema decision (#246)

**Status:** Decided. **Owner issue:** NERC-CEH/dri-one#246.
**Implemented by:** #235 (V1, the landing shape) and V2 (the target shape, after #236 and the
removal of SQLite; it absorbs #244).
**Referenced by:** #235, #238, #244, #243, #194. Those issues link here and don't make their own
schema decisions.

To change anything below, update #246 and this file in the same MR. Don't change it inside an
implementing issue.

**Short version:** one fact table plus a `documents` dimension table, a surrogate key with
insert-only raw rows, `timestamptz` count periods (`counted_from`/`counted_until`), and rollups in
separate tables. We get there in two migrations: V1 keeps today's two-table shape so the data can be
copied over as-is, and V2 builds the target shape once the SQLite rollback window has closed.

---

## Target shape (V2)

```sql
CREATE TABLE documents (
    document_id  text PRIMARY KEY,
    doc_title    text,              -- NULL = never resolved (repository read failed)
    record_type  text,
    removed_at   timestamptz        -- set when the catalogue no longer has the record; row is kept
);
CREATE INDEX idx_documents_record_type ON documents (record_type);

CREATE TABLE metric_counts (
    id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id    text        NOT NULL REFERENCES documents (document_id),
    metric_type    text        NOT NULL CHECK (metric_type IN ('view', 'download')),
    counted_from   timestamptz NOT NULL,
    counted_until  timestamptz NOT NULL,
    amount         integer     NOT NULL
);
COMMENT ON COLUMN metric_counts.counted_from  IS 'Start of the period amount was counted over (inclusive)';
COMMENT ON COLUMN metric_counts.counted_until IS 'End of the period amount was counted over (exclusive)';

CREATE INDEX idx_metric_counts_document_type
    ON metric_counts (document_id, metric_type)
    INCLUDE (amount);
CREATE INDEX idx_metric_counts_counted_from
    ON metric_counts (counted_from)
    INCLUDE (counted_until, document_id, metric_type, amount);
```

### Columns `counted_from` and `counted_until`

Each row is one document's count of one metric over one sync period. `amount` is the number counted
between `counted_from` and `counted_until`.

* **`counted_from`** is when the previous sync ran (`lastRun`).
* **`counted_until`** is when this sync ran. It's taken once per sync, so every row a sync writes
  shares the same value.
* **Half-open range:** `counted_from` is included and `counted_until` isn't. Each sync's
  `counted_until` equals the next sync's `counted_from`, so the periods meet with no gap and no
  overlap.
* **Normal length** is one hour. Expect longer periods after a database outage, when counts are held
  in memory and written in one go. Until #248 is fixed, expect a `counted_from` of 1970-01-01 on the
  first sync after a restart.
* **Renamed in V2** from `start_timestamp`/`end_timestamp`. V1 and the #236 copy keep the old names,
  so the copy stays a straight one.

## 1. Table shape: one fact table with a `metric_type` discriminator

| Query | Two tables (today) | One table (decided) |
|---|---|---|
| Per-document total (#242) | `idx_<t>_document_amount` covers it | The same, via `(document_id, metric_type) INCLUDE (amount)`. Both totals can also come from one query (`GROUP BY metric_type`) instead of two per page render. |
| Filtered/ordered report (#243) | `UNION ALL` of two tables. The `WHERE` is built once, substituted twice and every parameter is bound twice by index arithmetic (the "fragile" issue in #235). Every filter and index exists twice. | One scan, with `sum(amount) FILTER (WHERE metric_type = 'view')` per document, joined to `documents`. No union and no duplicate binding. Ordering and paging run on one relation. |
| Monthly bucketing (#194) | Two `GROUP BY`s, then a merge | One `GROUP BY date_trunc('month', counted_from, 'Europe/London'), metric_type` |

**Cost:** one extra column in the index key, and a predicate on queries that want only one metric.
Both are negligible. A third metric would be a new `CHECK` value, not a new table.

## 2. Primary key and write pattern: surrogate `id`, insert-only raw rows

We rejected a natural key on `(document_id, metric_type, counted_from)` with an upsert per period
for the raw table:

* **#248:** `lastRun` starts at 0, so every restart writes a period that starts at 0. A natural key
  would collide across restarts until #248 is fixed.
* **#247:** `amount` is currently a count of distinct addresses in a period. Two periods can't be
  merged by adding them up without counting some addresses twice, so an upsert that adds amounts
  together would give wrong numbers.

Natural keys with upsert belong in the **rollup tables** (§4). That's where #238's option 5 fits:
a rollup row means "this document, this metric, this calendar period", and adding to it is correct.
If #247 switches to counting requests, `amount` becomes safe to add up. Raw rows could then also be
upserted per aligned hour, which would only need an index change, not a redesign.

## 3. Dimension normalisation: yes, a `documents` table

The title and record type are stored once per document. Consequences:

* `updateDB` no longer rewrites the fact table. It touches only `documents` (thousands of rows, not
  millions), and only the rows whose title or type changed. The nightly rewrite of the whole table
  goes away, along with its dead tuples, index bloat and autovacuum load on the shared VM.
* Fact rows are never updated after they're inserted, so no fact-table index can block a HOT update.
  The report's `record_type IN (…)` filter is served by `idx_documents_record_type` through the
  join, not by an index on the fact table.

## 4. Rollup and retention: one raw table now, rollups as separate tables later

* V2 creates only the raw table. #238 adds rollup tables in their own migrations, for example
  `metric_counts_monthly (document_id, metric_type, month, amount, PRIMARY KEY (document_id, metric_type, month))`.
  These are new tables, so the fact table doesn't change.
* **Assumption, flagged for #238:** raw rows are kept indefinitely until #238 answers "how far back
  do reports need to go". Nothing in V2 depends on that answer. If #238 chooses time-based retention
  on raw rows at a scale where `DELETE` is too expensive, the follow-up is to partition
  `metric_counts` by month on `counted_from`, or to add a BRIN index on `counted_from` for the
  retention deletes. Either is one migration on one table, not a redesign.

## 5. Deleted documents: keep the dimension row and mark it

* A `documents` row is **never deleted because the catalogue record disappeared**. When the
  repository reports a record as not found, `updateDB` sets `removed_at` and skips that document on
  later nights. Today it logs an error every night for ever. The foreign key always holds, and
  historic counts are still reported under their last-known title, as they are today. #243 can
  filter `removed_at IS NULL` if it wants to.
* When `syncDB` can't read a document, it **still records the counts**. It creates the `documents`
  row if it's missing (`ON CONFLICT DO NOTHING`, with title and type NULL). Today it drops that
  period's counts. The next successful read fills in the title.
* The only path that deletes a `documents` row is the explicit admin purge (`deleteMetricsFor`). It
  deletes the fact rows first. Pruning old data is #238's job; this schema only allows it.

## 6. Timestamps: `timestamptz`, converted in V2 (absorbs #244)

#244 deferred the conversion so that #236 stays a straight copy. V2 runs after #236 and rewrites
the data anyway, so it converts and renames at the same time and avoids a separate rewrite:

```sql
INSERT INTO metric_counts (document_id, metric_type, counted_from, counted_until, amount)
SELECT document, 'view', to_timestamp(start_timestamp), to_timestamp(end_timestamp), amount FROM views
UNION ALL
SELECT document, 'download', to_timestamp(start_timestamp), to_timestamp(end_timestamp), amount FROM downloads;
```

`to_timestamp` is exact, so the converted data can be checked against the original epoch seconds.
In Java, read and write both columns as `OffsetDateTime`, not `long`.

**Calendar bucketing time zone: `Europe/London`.** `date_trunc` on `timestamptz` otherwise uses the
session time zone, and a view at 00:30 on 1 November London time is still 31 October in UTC. Every
calendar query names the zone explicitly so the result doesn't depend on server or session
configuration:

```sql
date_trunc('month', counted_from, 'Europe/London')
```

A period is assigned to the month its `counted_from` falls in. Periods are normally an hour long,
so very few cross a month boundary. Until V2, `date_trunc('month', to_timestamp(start_timestamp),
'Europe/London')` gives the same result.

## 7. Index list (owned here; #235 and V2 implement it; #243 supplies requirements)

| Index | Serves |
|---|---|
| `metric_counts (document_id, metric_type) INCLUDE (amount)` | Per-document totals as an index-only scan (#242's covering index carried forward). `amount` is never searched on; it's included only so the sum can be read from the index without visiting the table. Also covers the foreign key, so `deleteMetricsFor` doesn't need a full scan. |
| `metric_counts (counted_from) INCLUDE (counted_until, document_id, metric_type, amount)` | Report date range (`counted_from >= ? AND counted_until <= ?`) and monthly bucketing, both as index-only scans. `counted_from` is the only key column because it carries the range; after a range, another key column couldn't narrow the scan further. The table is insert-only, so the visibility map stays current and index-only scans really do skip the table. |
| `documents (record_type)` | Report `record_type IN (…)` |
| *(none)* for `docId LIKE '%…%'` | A leading wildcard can't use a b-tree index. The filter needs redesigning in #243. |

**H2 caveat:** H2 doesn't support `INCLUDE`. Run the V2 schema tests against real PostgreSQL
(#237), not H2. If H2 has to stay, list the included columns as trailing key columns instead
(`(document_id, metric_type, amount)` and `(counted_from, counted_until, document_id, metric_type, amount)`).
They cover the same queries with slightly larger indexes.

V1 keeps #242's `(document, amount)` as plain key columns: its script also runs on H2, and it
matches the index name and shape already on the SQLite file.

## Sequencing: why two migrations, and what V1 is

While the SQLite rollback window is open (#234), switching engine must work **with the same image**.
`JDBCMetricsService` runs the same SQL on both engines, so that SQL has to keep working against the
production SQLite file. That file is in the two-table shape and must not be restructured: it's
1.1 GB on a CIFS share. Moving PostgreSQL to the target shape now would mean two parallel
data-access paths for the length of the window, and #236 couldn't reconcile table by table.

* **V1 (#235, now):** today's two-table, denormalised shape with today's column names
  (`start_timestamp`/`end_timestamp`, `bigint` epoch seconds), so #236 stays a straight copy and
  reconciles row by row. It adds a surrogate `id` (insert-only, as in §2), #242's covering
  `(document, amount)` index and a `(start_timestamp, end_timestamp)` index. It does **not** add a
  `record_type` index: that column moves to `documents` in V2, and indexing it on the fact tables in
  the meantime would stop `updateDB`'s nightly update from being HOT. Until V2, `updateDB` should
  rewrite only the rows whose title or type actually changed.
* **V2 (after #236 is verified and the SQLite path is removed):** builds the target shape above from
  `views`/`downloads` with `INSERT … SELECT`, renames the period columns to
  `counted_from`/`counted_until`, converts them to `timestamptz` (#244) and drops the old tables.
  It ships in the same release that switches the service to the new SQL, so only one code path ever
  exists.

## Confirmed supported without further redesign

* **Per-document total (#242):** yes, an index-only scan.
* **Filtered/ordered report (#243):** yes, one relation plus a join to `documents`, with the date
  range as an index-only scan. The `docId` filter is #243's redesign.
* **Monthly bucketing (#194):** yes, a single `GROUP BY date_trunc('month', counted_from, 'Europe/London')`.
* **Calendar-aware queries (#244):** yes, `timestamptz` from V2.
