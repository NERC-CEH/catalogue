# Vector Search and MCP Server

## Overview

Two independent additions to the catalogue:

1. **Dense vector search** — semantic KNN search via Solr's `DenseVectorField`, complementing the existing BM25 full-text search
2. **MCP server** — exposes catalogue search to external LLMs (Claude, etc.) using the Spring AI MCP starter, activated via a Spring profile

Both features use **Spring AI 2.0** (requires Spring Boot 4.0) and **Amazon Bedrock** for embeddings.

---

## 1. Embedding service

**Amazon Bedrock — Titan Embed Text v2** (`amazon.titan-embed-text-v2:0`)

- Managed AWS service — no self-hosted containers
- 1024-dimensional vectors
- AWS credentials from environment (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`) or IAM role

Alternative: Cohere Embed v3 (`cohere.embed-english-v3`, also 1024 dims) — same Solr schema works for either.

### Activation

Add `vector-search` to `SPRING_PROFILES_ACTIVE`. Requires Bedrock credentials in the environment:

```bash
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_REGION=eu-west-2
```

Without these, the `EmbeddingModel` bean is absent; indexing continues without vectors and
documents remain searchable via BM25.

## 3. Solr schema changes

Add to `solr/documents/conf/managed-schema` before `</schema>`:

```xml
<!-- Vector search -->
<fieldType name="knn_vector_1024" class="solr.DenseVectorField"
           vectorDimension="1024" similarityFunction="cosine"
           knnAlgorithm="hnsw"/>

<field name="vector"               type="knn_vector_1024" indexed="true"  stored="false"/>
<field name="embedding_text"       type="string"          indexed="false" stored="true"/>

<!-- Temporal coverage — stored for embedding, not BM25-searched -->
<field name="temporal_extent_text" type="string"          indexed="false" stored="true"/>

<!-- Supporting document full text — BM25-searchable, not stored -->
<field name="document_text"        type="text_general"    indexed="true"  stored="false"/>
```

A **full Solr reindex** is required after applying schema changes (trigger via the admin `/index`
endpoint). This is required for:
- Any new `<field>` or `<fieldType>` additions
- Changes to the `document_text` field (new BM25 content)
- Changes to the `temporal_extent_text` field (new embedding input)

## 4. Indexing pipeline

### Embedding text fields

Only semantically meaningful fields go into the embedding text. Administrative fields (state, licence, catalogue) are excluded to avoid false similarities:

| Field | Reason |
|-------|--------|
| `title` | Most important signal |
| `description` | Core content |
| `keyword` | Domain concepts |
| `altTitle` | Synonyms |
| `objectives` | Research purpose |
| `observedPropertyTitle` | What is measured |
| `keywordsParameters` | Measured parameters |
| `supplementalDescription` | Additional text |
| `temporalExtentText` | Data collection period in natural English (e.g. "Data collected from 2000 to 2015") |
| Supporting document text | PDF/Word/RTF content extracted via Tika (see section 4b) |

`temporalExtentText` is generated by `SolrIndexGeminiDocumentGenerator` from `GeminiDocument.temporalExtents` (a `List<TimePeriod>` with `LocalDate begin/end`). It is not searchable via BM25 — stored only for embedding and debugging.

### Debounced embedding (PendingEmbeddingService)

Embedding is **decoupled from the main indexing path** to avoid calling Bedrock on every rapid save:

1. `SolrIndexMetadataDocumentGenerator.generateIndex()` marks the document ID in `PendingEmbeddingService` (no Bedrock call)
2. BM25 fields are committed to Solr immediately — the document is searchable at once
3. A `@Scheduled` flush (default: every 5 minutes) processes all pending IDs in configurable batches, calling Bedrock once per unique ID and doing a **partial Solr atomic update** of only `vector` + `embedding_text`

Multiple rapid saves of the same document result in one Bedrock call (the pending map overwrites the previous entry).

### Full reindex (server restart / empty index)

`SolrScheduledReindexService` detects an empty index and rebuilds it. All document IDs are marked pending during the rebuild. When the flush fires, the base documents already exist in Solr (committed during rebuild), so partial atomic updates succeed. The flush processes IDs in configurable batches to avoid Bedrock rate limits.

**Configuration:**
```properties
catalogue.embedding.flush-delay=PT5M
catalogue.embedding.batch-size=50
catalogue.embedding.inter-batch-pause-ms=1000
```

## 4b. Supporting document extraction

PDF, Word (`.doc`/`.docx`), and RTF files associated with a catalogue record can be extracted
by Apache Tika and included in the embedding text. This allows semantic queries like "peat bog
carbon flux methodology" to match records whose metadata only says "carbon flux monitoring".

### Enabling it

Mount the supporting documents directory into the container and set the configuration property:

**`docker-compose.yml`** (catalogue service):
```yaml
volumes:
  - /path/to/supporting-documents:/var/ceh-catalogue/supporting-documents:ro

environment:
  CATALOGUE_SUPPORTING_DOCUMENTS_LOCATION: /var/ceh-catalogue/supporting-documents
```

**Or via `override.env`:**
```properties
CATALOGUE_SUPPORTING_DOCUMENTS_LOCATION=/var/ceh-catalogue/supporting-documents
```

The expected directory structure is `{location}/{documentId}/` with document files directly
inside. For example:
```
/var/ceh-catalogue/supporting-documents/
  2d023ce9-6dbe-4b4f-a0cd-34768e1455ae/
    user-guide.pdf
    data-dictionary.docx
```

### What gets extracted

- File types: `.pdf`, `.doc`, `.docx`, `.rtf` only — raw data files (CSV, NetCDF, zip) are skipped
- Up to `catalogue.embedding.doc-max-files` files per record (default: 5)
- Up to `catalogue.embedding.doc-max-chars` characters per file (default: 4 000)
- Combined text is capped at 30 000 characters before sending to Bedrock
- If no supporting documents exist, extraction returns `""` and embedding uses metadata only

When absent (property not set), `SupportingDocumentExtractor` is not instantiated and the
system behaves exactly as before.

### BM25 search

The same extracted text is also written to the `document_text` Solr field (type `text_general`,
indexed but not stored), making it searchable via keyword queries at boost `document_text^1`
— lower than `description^2` since document content may be verbose and less curated.

A full Solr reindex is required to populate `document_text` for existing records.

### Security

`SupportingDocumentExtractor.extractText(documentId)` validates that the resolved path stays
within the configured base directory before accessing the filesystem. IDs containing `..`
sequences are rejected with a `WARN` log entry and return empty string.

**Configuration properties:**
```properties
# Set to enable (absent = disabled):
# catalogue.supporting-documents.location=/var/ceh-catalogue/supporting-documents
catalogue.embedding.doc-max-chars=4000
catalogue.embedding.doc-max-files=5
```

## 5. Semantic search

### Endpoint

```
GET /{catalogue}/documents?term=river+flow&semantic=true
GET /documents?term=river+flow&semantic=true
```

When `?semantic=true`, `SearchController` routes to `SemanticSearcher` (if present).

### KNN query

```
q={!knn f=vector topK=20}[0.1,0.2,...]
fq=locations:"IsWithin(ENVELOPE(...))"   (if bbox supplied)
fq={!term f=catalogue}eidc
fq=state:published AND view:public
```

The same permission/catalogue filters as BM25 search are applied. Spatial `bbox` filtering works identically to the existing search.

### Geospatial + semantic

Pass `?bbox=minLon,maxLon,maxLat,minLat&semantic=true` to find the most semantically relevant records *within a geographic area*. Solr's KNN parser applies the spatial filter before ranking, so the result is "closest in meaning, constrained by location".

Named place-name keywords (e.g. "United Kingdom", "Cairngorms") flow naturally into the embedding text, so location-based queries like "soil carbon monitoring Scotland" work without reverse geocoding.

### Access control

Access to `?semantic=true` can be restricted to a Crowd group:

```properties
catalogue.semantic.group=MY-GROUP-NAME
```

- When set: only users in that group see the semantic search toggle in the UI; unauthorised
  requests silently fall back to BM25 (no error, no information leakage)
- When empty (default): unrestricted — all authenticated and public users can use semantic search
- Public users are implicitly excluded when a group is set (they have no Crowd groups)

### Search UI toggle

`SearchResults` carries a `semanticEnabled` boolean (populated by `SearchController` based on
the user's group membership and whether `SemanticSearcher` is present). The Freemarker template
`search.ftlh` conditionally renders a Bootstrap switch toggle inside the search form:

```freemarker
<#if semanticEnabled>
<div class="form-check form-switch mt-2">
  <input class="form-check-input" type="checkbox" name="semantic" value="true">
  <label class="form-check-label">Semantic search</label>
</div>
</#if>
```

The toggle is **absent from the DOM** for unauthorised users — no JS-side permission logic is
required. When checked, `SearchApp.js` adds `semantic=true` to the query string; when unchecked
it is omitted (the model's `getState()` excludes falsy values). Bookmarked `?semantic=true` URLs
restore the checkbox state on page load via the router.

## 6. MCP server

### Activation

Add `mcp-server` to `SPRING_PROFILES_ACTIVE`:

```bash
SPRING_PROFILES_ACTIVE=development,server-eidc,search-basic,cache,service-agreement,upload-simple,mcp-server
```

### Transport (SSE, WebMVC)

- `GET  /mcp/sse`      — SSE event stream
- `POST /mcp/messages` — client-to-server messages

### Available tools

| Tool | Description |
|------|-------------|
| `searchCatalogue` | Full-text BM25 search |
| `semanticSearch` | Vector similarity search (requires `vector-search` profile) |
| `hybridSearch` | RRF fusion of BM25 + KNN (requires `vector-search` profile) |
| `getDocument` | Retrieve a record by ID |
| `listCatalogues` | List available catalogues |

Permission filtering is applied automatically — all MCP searches run as the public user and only return published records.

### Hybrid search — Reciprocal Rank Fusion

`hybridSearch` combines BM25 keyword ranking and KNN vector ranking in a **single Solr request**
using Solr 10's native `{!rrf}` query parser:

```
q={!rrf queries=$bm25q,$knnq k=60}
bm25q={!edismax qf="title^5 description^2 ..."}search term
knnq={!knn f=vector topK=100}[0.1,0.2,...]
```

RRF score: `Σ 1 / (k + rank_i)` across sub-queries, where `k=60` (RRF paper default).

**Why hybrid over pure semantic?**
- BM25 is precise for exact dataset names, accession numbers, and rare technical terms
- KNN has better recall for concept queries where keywords don't appear verbatim
- RRF fusion rewards documents that rank well on both axes without requiring calibrated scores

**topK multiplier**: the KNN sub-query uses `topK = min(rows × 5, 200)` so the vector side
supplies enough candidates for fusion. At the default 20 results this gives `topK=100`.

### Upgrade path

Spring AI 2.0 uses `MethodToolCallbackProvider` with `@Tool`-annotated methods. No changes are needed when upgrading Spring AI versions — the API is stable.

## 7. Summary of new components

```
Amazon Bedrock (Titan Embed Text v2)       ← embedding service (cloud, no container)
  ↑ called by
PendingEmbeddingService                    ← scheduled flush, partial Solr atomic updates
  ↑ feeds from
SolrIndexMetadataDocumentGenerator         ← marks document ID on each index
  + SupportingDocumentExtractor (optional) ← Tika PDF/Word/RTF extraction (also → document_text)
  + SolrIndexGeminiDocumentGenerator       ← adds temporalExtentText from GeminiDocument.temporalExtents

SemanticSearcher                           ← KNN Solr query + permission filters
  ↓ results via
SearchController                           ← adds semanticEnabled flag → Freemarker toggle
  ↓ UI toggle in
search.ftlh                                ← shown only to users with catalogue.semantic.group access

McpServerConfig + CatalogueMcpTools        ← behind mcp-server profile
  ↓ delegates to existing Searcher beans
  ↓ + HybridSearcher (RRF fusion, requires vector-search)
  exposed via SSE to Claude / other LLMs
```

No new Docker Compose services are required. Amazon Bedrock replaces Ollama as the embedding
provider. Supporting documents require a volume mount and property; temporal extent text requires
no additional configuration.

## 8. Property reference

| Property | Default | Purpose |
|----------|---------|---------|
| `catalogue.embedding.flush-delay` | `PT5M` | How often to flush pending embeddings (ISO-8601) |
| `catalogue.embedding.batch-size` | `50` | Documents per Bedrock batch call |
| `catalogue.embedding.inter-batch-pause-ms` | `1000` | Pause between batches (ms) |
| `catalogue.embedding.doc-max-chars` | `4000` | Max characters extracted per supporting document |
| `catalogue.embedding.doc-max-files` | `5` | Max supporting documents processed per record |
| `catalogue.semantic.group` | *(empty)* | Crowd group required for `?semantic=true`; empty = unrestricted |
| `catalogue.supporting-documents.location` | *(absent)* | Filesystem path for supporting documents; absent = disabled |
